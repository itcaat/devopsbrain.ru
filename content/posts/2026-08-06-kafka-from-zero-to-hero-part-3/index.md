В предыдущей части наш интернет-магазин вырос, и мы распределили события заказов между Partition, используя `orderId` как ключ. Теперь предлагаю немного приблизить картинку: выберем одну Partition и посмотрим, что Kafka физически хранит внутри неё.

Иногда Kafka представляют как большую очередь сообщений, которая живёт где-то в памяти. На практике всё гораздо прозаичнее: в основе Kafka лежит обычный журнал на диске.

## Partition — это "просто" лог

Каждая Partition — упорядоченная последовательность записей:

```text
Partition 0

Offset 0  OrderCreated      orderId=48291
Offset 1  PaymentCompleted  orderId=48291
Offset 2  DeliveryStarted   orderId=48291
Offset 3  OrderDelivered    orderId=48291
```

Такой журнал называют append-only log: новые записи добавляются только в конец. Kafka не приходится искать место для вставки или сдвигать уже записанные данные.

Последовательная запись крупных блоков помогает эффективно использовать накопители и файловый кэш ОС. К механизмам производительности вернёмся далее. Пока я предлагаю запомнить одну мысль: новое сообщение продолжает историю, а не переписывает предыдущие записи.

## Что представляет собой сообщение

Сообщение в Kafka называется Record. Упрощённо его можно представить так:

```text
+-----------------------+
| Key                   |
| Value                 |
| Timestamp             |
| Headers               |
+-----------------------+
```

Value — полезная нагрузка сообщения. JSON, Avro, Protobuf, строка или произвольные бинарные данные — для Kafka это просто байты.

Для начала покажем только бизнес-данные об оплате заказа. Это упрощённый пример Value: далее добавим сведения, которые помогут получателям различать события и безопасно обрабатывать их.

```json
{
  "orderId": 48291,
  "status": "paid",
  "price": 4999
}
```

Как мы уже говорили ранее – Key часто используется при выборе Partition. В нашем магазине таким ключом служит `orderId`, например `48291`.

При стандартном key-based partitioning одинаковый ключ будет направляться в одну и ту же Partition, пока количество Partition не меняется. Поэтому события одного объекта можно обрабатывать в правильном порядке.

Timestamp — временная метка записи. Её смысл зависит от настройки топика message.timestamp.type:

- CreateTime — время, которое задаёт Producer. Приложение может явно указать момент события, например время оформления заказа. Если время не указано, Producer подставляет время создания записи.
- LogAppendTime — время добавления записи в журнал Kafka. Его устанавливает Broker, заменяя временную метку, присланную Producer.

Например, заказ оформлен в 12:00, а запись о нём попала в Kafka в 12:05. При CreateTime она может сохранить метку 12:00, если приложение передало время заказа. При LogAppendTime метка будет 12:05. Поэтому Timestamp нельзя автоматически считать временем самого события: нужно знать конфигурацию топика и то, как Producer заполняет это поле.

Headers позволяют передавать дополнительные метаданные: например, `TraceID`, `Content-Type` или `RequestID`.

## Offset

После попадания в Partition запись получает Offset — её позицию внутри журнала. Offset не является глобальным ID сообщения. Он уникален только в пределах конкретной Partition.

Здесь проявляется важное отличие Kafka от традиционной очереди: чтение сообщения не удаляет его из журнала. Kafka хранит записи согласно политике хранения, поэтому их можно прочитать повторно, а разные приложения могут независимо обрабатывать один и тот же поток событий.

![alt text](images/image02.png)

Consumer может сохранить позицию, с которой его группа продолжит чтение после перезапуска. Её называют `committed offset`. Для каждой Partition позиция сохраняется отдельно: например, после обработки записи с offset `100` группа сохраняет `101` — offset следующей записи. После сбоя чтение возобновляется с сохранённой позиции, поэтому записи, обработанные после последнего сохранения, могут прийти повторно.

{{< callout type="tip" text="При стандартном механизме фиксации позиций Kafka хранит committed offsets во внутреннем топике __consumer_offsets. Каждая позиция относится к конкретной связке Consumer Group, Topic и Partition." >}}

Различие между текущей позицией чтения и сохранённой позицией подробнее описано в разделе [Consumer Position](https://kafka.apache.org/41/design/design/#consumer-position).

Возврат к более раннему offset и повторное чтение доступной истории называют Replay. Например, аналитика магазина может заново обработать события заказов после исправления ошибки в расчётах. Само повторное чтение не отменяет уже выполненные действия: если Consumer отправляет письма или начисляет бонусы, приложение должно учитывать последствия повторов.

Replay возможен только пока нужные записи остаются в Kafka. Политику хранения называют retention. В следующих частях подробно разберём её настройки и рассмотрим, когда сохранять committed offset, чтобы учитывать сбои и повторную обработку.

## Что происходит при записи

Если сильно упростить путь сообщения — Producer отправляет record. Partitioner выбирает Partition, запрос попадает на Broker, который является её leader, а запись добавляется в лог.

![alt text](images/image01.png)

Kafka не нужно искать старую запись и изменять её на месте. Основной сценарий — дописать новые данные в конец. И получается вместо постоянного изменения состояния мы получаем последовательную историю событий.

Offset естественным образом отвечает на вопросы:

- Что было раньше?
- Что читать следующим?
- До какого места дошёл Consumer?
- Откуда начать повторное чтение?

Поэтому в Kafka основной адрес записи выглядит примерно так:

```text
Topic + Partition + Offset
```

Например:

```text
orders.events / partition 2 / offset 58213
```

Но пока здесь есть очевидная проблема. Если вся Partition физически находится на одном Broker, что произойдёт, когда этот Broker упадёт? Для этого в Kafka существует репликация.

Далее разберём Leader, Follower, ISR и посмотрим, как Kafka переживает потерю Broker.
