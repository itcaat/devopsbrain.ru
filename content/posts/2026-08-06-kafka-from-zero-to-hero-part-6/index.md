Называть Kafka «просто очередью сообщений» — всё равно что называть Kubernetes «скриптом для запуска контейнеров». Технически верно, но скрывает главный архитектурный потенциал.

Kafka может использовать один и тот же `Topic` сразу в двух режимах:

1. **Как очередь задач (Queue):** распределение работы между воркерами.
2. **Как журнал событий (Event Stream):** трансляция фактов для множества независимых систем.

Поэтому Kafka корректнее называть **Event Streaming Platform**.

## 1. Kafka в роли очереди (Task Queue)

В классической модели очереди одна задача должна быть обработана строго **одним** воркером. В Kafka это реализуется через механизм **Consumer Group**.

```text
               video-processing (Topic)
             /            |            \
       Partition 0   Partition 1   Partition 2
            |             |             |
        Worker A      Worker B      Worker C
        \__________________________________/
          Consumer Group: transcoding-workers
```

* **Принцип:** Kafka распределяет партиции внутри группы так, чтобы каждое сообщение попало только в один `Consumer`.
* **Применение:** асинхронные и «тяжелые» задачи: кодирование видео, генерация отчетов, отправка email, фоновый импорт данных.
* **Backpressure Buffering:** Kafka выступает амортизатором нагрузки. Если продюсер шлет 100 000 сообщений в секунду, а воркеры успевают разобрать только 20 000, данные сохраняются в лог без потери и падения сервисов.
* **Главное отличие от RabbitMQ/SQS:** в классической очереди сообщение удаляется сразу после обработки. В Kafka оно остается в логе до истечения `retention.ms`, а воркер лишь продвигает свой `Offset`.

## 2. Kafka как потоковая платформа (Publish/Subscribe)

В потоковой модели сообщение — это не директива «сделай действие», а зафиксированный факт: «Что-то произошло» (OrderPaid, UserRegistered, FlightPriceChanged).

Одно событие могут одновременно и независимо читать разные сервисы, создавая собственные Consumer Group.

```text
OrderPaid (Topic)
                                   |
        +--------------------------+--------------------------+
        |                          |                          |
        v                          v                          v
Consumer Group:          Consumer Group:          Consumer Group:
Delivery Service         Analytics Service        Fraud Detection
(создает доставку)       (считает метрики)        (проверяет фрод)
```

Каждая группа получает полную копию потока. Обработчики не влияют друг на друга и читают данные со своей скоростью.

## 3. Сравнение подходов: Queue vs Stream

| Характеристика | Модель очереди (Queue) | Потоковая модель (Stream) |
| :--- | :--- | :--- |
| **Ключевой вопрос** | «Кто должен сделать эту задачу?» | «Кому интересен этот факт?» |
| **Сущность** | Задача (`Task`) | Событие (`Event`) |
| **Обработка** | Один воркер внутри группы | Множество независимых `Consumer Groups` |
| **Жизненный цикл** | Считается завершенным после чтения | Сохраняется в логе для повторного чтения |
| **Типичные кейсы** | Транскодинг, генерация PDF | Реализованный CTR, аналитика, антифрод, CDC |

## 4. Совмещение моделей в одном Topic

Сила Kafka в том, что один Topic обслуживает обе модели одновременно.

Пример для топика `orders`:

* Группа `delivery-workers` читает его как очередь: распределяет задачи на отправку товара.
* Группа `analytics-service` читает тот же топик как поток: выстраивает графики продаж.
* Группа `fraud-detection` анализирует его как поток: ищет подозрительные паттерны.

## 5. Команды против событий (Commands vs Events)

Для правильного проектирования архитектуры важно различать тип сообщений:

* **Команда (`Command`):** выражение намерения. Имеет конкретного исполнителя: `SendWelcomeEmail`.
* **Событие (`Event`):** факт из прошлого. Не знает, кто его прочитает: `UserRegistered`.

Событийный подход (`Event-Driven`) снижает связность систем: при добавлении нового сервиса, например программы лояльности, продюсер не меняется — новый сервис просто подписывается на существующий топик.

### Резюме

Kafka объединяет в себе функции очереди, Publish/Subscribe, распределённого журнала и долговременного хранилища. Её ключевая ценность — возможность читать один и тот же поток данных параллельно, разным сервисам и в разных архитектурных ролях.
